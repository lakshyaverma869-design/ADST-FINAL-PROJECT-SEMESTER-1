# Project Explanation and Viva Preparation

## 1. Project overview

**Title:** Dynamic EV Charging Forecasting using City Traffic Data

This project demonstrates a city-level estimate of hourly EV charging demand. A Flask web app supports Live Prediction, Historical Analysis, and Future Forecast. Users choose a supported city; the app retrieves available weather automatically and uses an optional live road-segment traffic indicator when a TomTom key is configured. It applies a Random Forest regression pipeline and saves estimates and source details in SQLite.

## 2. Problem statement and objective

Charging demand changes over time. The project demonstrates how time, weather, and a traffic-status indicator can be presented to a regression model to estimate sessions for one city-hour. It is a learning prototype, not an operating tool. The actual charging-session target is not available, so the included training labels are synthetic and every app result is identified as a model estimate.

## 3. Data sources and what they mean

- **Training CSV:** 8,640 synthetic city-hour records generated by `generate_data.py`. It covers 90 illustrative days, 24 hours per day, and four cities. Its traffic volume, speed, EV count, weather, and charging sessions are generated values, not observations.
- **Current and forecast weather:** Open-Meteo returns current conditions and hourly forecast. The forecast is used only when the selected hour is returned by the service; the configured maximum is 16 days.
- **Historical weather:** Open-Meteo's archive returns model-based historical weather reanalysis, not necessarily a direct observation from a nearby station. Historical Analysis allows up to 31 days per request.
- **Optional live traffic:** TomTom Flow Segment Data can provide current and free-flow speeds with confidence for the nearest road segment to a configured city reference point. It is not citywide volume, requires a key, and may be unavailable.
- **Unavailable sources:** No actual charging-session data, EV counts, citywide traffic counts, or historical traffic feed is configured. Missing traffic is explicitly `unknown`; these fields are never invented.

The project links the [Open-Meteo forecast documentation](https://open-meteo.com/en/docs), [Open-Meteo historical weather documentation](https://open-meteo.com/en/docs/historical-weather-api), and [TomTom Flow Segment Data documentation](https://docs.tomtom.com/traffic-api/documentation/tomtom-maps/v1/traffic-flow/flow-segment-data).

## 4. Features and target

The model input fields are city, local hour, weekday, traffic status, temperature, rainfall, weather category, and relative humidity. `peak_period` is derived from the hour: commute peak is 07:00–10:00 and 16:00–20:00, daytime is 11:00–15:00, and all other hours are off-peak.

The target is `charging_demand`, generated synthetic sessions per city-hour. `traffic_volume`, `average_speed`, and `ev_count` appear in the CSV to document the generator and support EDA; they are not deployed model inputs. The target generator uses these synthetic fields, so the fitted model cannot observe every factor used to make the training label.

## 5. End-to-end workflow

1. Generate reproducible synthetic city-hour data with a fixed seed.
2. Check duplicates, required target values, types, and descriptive statistics.
3. Derive traffic status for training and deliberately mark 20% of records as unknown to exercise missing-traffic behavior.
4. Derive `peak_period` from hour.
5. Split rows 80/20 with `random_state=42`.
6. One-hot encode categorical fields and impute missing numeric values inside a scikit-learn pipeline.
7. Fit `RandomForestRegressor`; calculate MAE, MSE, RMSE, R², and feature importance from the run.
8. Save the pipeline and metrics for the Flask app; create labelled training charts and generated-data observations.
9. For a user request, validate city and date/time, retrieve weather, use traffic only when available, build the shared feature row, predict, and record the source details.
10. Save successful predictions, API cache entries, and historical analysis reports in SQLite.

## 6. Three app modes

- **Live Prediction:** Current city-local hour and current weather, with optional TomTom road-segment status.
- **Historical Analysis:** Selected historical weather range, hourly model estimates, calculated summaries and charts, and a downloadable report. Historical traffic remains unavailable.
- **Future Forecast:** Selected future city-hour. Forecast weather is used inside the returned API horizon. Farther dates may use an average of up to five earlier same-date/hour weather records and are labelled historical analogues, not forecasts.

Each mode shows the source, retrieval status, and relevant limitations. If weather cannot be retrieved and no cache is available, the app shows an error instead of substituting made-up values.

## 7. Model design and evaluation

The task is regression because the output is a numeric estimate. The app uses `RandomForestRegressor` in a `Pipeline` with a `ColumnTransformer`. One-hot encoding handles city, traffic status, weather condition, and peak-period categories. Median imputation handles missing numeric inputs. Keeping preprocessing and estimator together makes training and app transformations consistent.

The training script computes:

- **MAE:** average absolute error, in sessions/hour.
- **MSE:** average squared error; large misses contribute more.
- **RMSE:** square root of MSE, in sessions/hour.
- **R²:** comparison against a mean-target baseline; it may be negative.

These measurements use a random holdout from the synthetic dataset and do not indicate performance on real charging data, a future period, or unseen cities. Feature importance is calculated from the fitted forest and describes split usage, not causation.

## 8. Web app, report, and storage

`app.py` defines the Flask pages and prediction routes. `data_sources.py` contains the external weather and optional traffic clients, source labels, and cache behavior. `model_utils.py` is shared by training and the app. `report_generator.py` summarizes retrieved historical weather paired with model estimates and produces six charts.

SQLite stores predictions, source metadata, historical analysis summaries and rows, plus cached API responses. Current weather is cached for 20 minutes, forecasts for 30 minutes, historical weather for 12 hours, and current traffic for 5 minutes. If a source refresh fails, an expired cache can be used with a stale label and warning. The report route serves the report in the app and downloads a self-contained HTML copy with CSS and charts embedded.

## 9. Limitations and future work

The included dataset and target are synthetic. Weather inputs are available from a public provider, but archive weather is reanalysis. TomTom's optional endpoint describes one road segment. The project lacks real charging sessions, EV counts, citywide traffic volume, historical traffic, station capacity, charger availability, and event data. A random split may overstate how well the model would work on later dates.

Useful next work would collect permitted station-session and traffic records, evaluate with chronological holdout data, compare against simple baselines, add charger capacity and availability, and quantify uncertainty. Those extensions require suitable real observations.

## Viva questions and suggested answers

1. **What is the goal of the project?**  
   To demonstrate how a regression model can estimate hourly EV charging demand for a selected city using time, weather, and an optional traffic-status indicator.

2. **Is the included training data real?**  
   No. `generate_data.py` creates synthetic values for the dataset and charging-demand target.

3. **What does one training row represent?**  
   A generated record for one city at one hour on one date.

4. **What are the three prediction modes?**  
   Live Prediction uses current weather, Historical Analysis uses archived weather for a selected date range, and Future Forecast uses returned forecast weather when available.

5. **Which cities does the app support?**  
   Bengaluru, Delhi, Mumbai, and Pune, using fixed city reference coordinates and the India timezone.

6. **Where does current weather come from?**  
   Open-Meteo's public forecast API. The app identifies the source and retrieval or cache status.

7. **Are historical weather values direct station observations?**  
   They are Open-Meteo historical weather reanalysis values. The project labels them as reanalysis rather than direct station observations.

8. **How far ahead is the weather forecast?**  
   The configured Open-Meteo request asks for up to 16 days. The app uses forecast data only if the selected hour is returned; farther dates may use a labelled historical analogue.

9. **What does the optional TomTom traffic value represent?**  
   Current speed relative to free-flow speed for the nearest road segment to a configured city point. It is not citywide traffic volume and needs a key.

10. **What happens if traffic is unavailable?**  
    Traffic status is set to `unknown`. No volume or speed is fabricated, and the model was trained with unknown-traffic examples.

11. **Does the app have actual EV counts or charging sessions?**  
    No. There is no actual EV-count or charging-session feed configured. Demand outputs are model estimates based on synthetic training labels.

12. **Why is this a regression task?**  
    The target is a numeric sessions-per-hour estimate.

13. **Why use a Random Forest?**  
    It can capture nonlinear patterns and interactions and is straightforward for an introductory project. It is not claimed to be best for real data.

14. **What is feature engineering here?**  
    The app and training pipeline derive a `peak_period` category from the hour.

15. **What does one-hot encoding do?**  
    It represents categories such as city and weather as numeric indicator columns usable by the model.

16. **Why is preprocessing part of the pipeline?**  
    So the app applies the same imputation and encoding steps used during training.

17. **What do MAE and RMSE mean?**  
    Both are errors in sessions/hour. MAE is average absolute error; RMSE weights larger errors more strongly.

18. **Can the test score represent real-world accuracy?**  
    No. It measures a random holdout from the same synthetic generator, not real sessions or a future period.

19. **Why use SQLite and a cache?**  
    SQLite stores predictions and reports locally without a separate database server. The cache reduces repeated API requests and can provide labelled stale values during an outage.

20. **What is a practical next step?**  
    Collect permitted charging-session and traffic observations, then evaluate on a later time period before using the model operationally.
