# Dynamic EV Charging Forecasting using City Traffic Data

A local MCA end-semester project that estimates hourly EV charging demand in Bengaluru, Delhi, Mumbai, or Pune. It includes three city-only prediction modes, public weather integrations, an optional live road-flow indicator, a synthetic-data Random Forest model, a responsive Flask dashboard, SQLite history and API caching, and downloadable historical analysis reports.

> **Data integrity:** The included CSV and its `charging_demand` labels are fully synthetic. Open-Meteo supplies weather data to the app. TomTom traffic is optional and requires a key. No actual charging sessions, EV counts, citywide traffic volumes, or historical traffic observations are configured. The output is a model estimate, not an observed session count.

## What the project does

Users select only a supported city (and, for historical or future modes, a date/time). The app fetches weather and an optional traffic indicator, prepares model inputs, estimates sessions per hour, labels the source and availability of each value, and saves the result.

| Mode | User input | Weather source | Traffic input | Result |
| --- | --- | --- | --- | --- |
| Live Prediction | City | Current conditions | Optional TomTom flow for a nearby road segment; otherwise `unknown` | Current city-hour model estimate |
| Historical Analysis | City and date range (up to 31 days) | Open-Meteo historical weather reanalysis | Unavailable; passed as `unknown` | Hourly estimates, charts, observations, and an HTML report |
| Future Forecast | City and future city-hour | Open-Meteo hourly forecast when the selected hour is returned (up to 16 days); farther dates may use a labelled historical weather analogue | Unavailable; passed as `unknown` | Future city-hour model estimate |

The app does not accept guessed traffic or weather values from the user. If a required weather request fails and no cached copy is available, it explains the problem instead of creating a prediction from fabricated weather. Expired cached weather may be shown with a stale-data warning. For dates outside the forecast horizon, the same-date/hour weather analogue is explicitly labelled as an analogue, not a forecast.

## Data sources and limits

- **Open-Meteo Forecast API:** current conditions and hourly forecast, including temperature, humidity, rain, and weather code. See the [forecast API documentation](https://open-meteo.com/en/docs).
- **Open-Meteo Historical Weather API:** hourly historical weather reanalysis. These values are model-based reanalysis, not direct observations from a particular weather station. See the [historical API documentation](https://open-meteo.com/en/docs/historical-weather-api).
- **TomTom Flow Segment Data (optional):** current speed, free-flow speed, and confidence for the nearest road segment to the configured city point. This is a local segment indicator, not citywide traffic volume, and needs a user-supplied API key. See the [Flow Segment Data documentation](https://docs.tomtom.com/traffic-api/documentation/tomtom-maps/v1/traffic-flow/flow-segment-data) and [TomTom pricing](https://docs.tomtom.com/pricing).
- **Training data:** the 8,640-row CSV contains generated values for 90 days × 24 hours × 4 cities. Its generator and assumptions are documented in `generate_data.py`.
- **Charging-demand target:** generated by illustrative rules for the training exercise. All predictions from the fitted model are model estimates, not measured sessions.

Historical analysis charts and report text calculate observations from the selected API weather rows paired with model estimates. They label unavailable historical traffic and do not claim a measured relationship between traffic and actual charging sessions.

## Model and features

The target is `charging_demand`, a synthetic count per city-hour. The model is a scikit-learn `RandomForestRegressor` in a single preprocessing pipeline. Categorical fields are one-hot encoded; numeric fields are median-imputed. In 20% of the synthetic training records, traffic status is deliberately changed to `unknown` to cover the app's no-traffic case.

| Model field | Source in app | Notes |
| --- | --- | --- |
| `city` | Project city reference list | One of four supported Indian cities |
| `hour` | Local clock or selected target time | 0–23 |
| `day_of_week` | Local city calendar | Monday = 0 through Sunday = 6 |
| `traffic_status` | Optional TomTom current segment, else `unknown` | No volume or speed is invented |
| `temperature` | Open-Meteo weather | Celsius |
| `rainfall` | Open-Meteo weather | Millimetres |
| `weather_condition` | Open-Meteo WMO weather code | Mapped to a small set of categories |
| `relative_humidity` | Open-Meteo weather | Percent |
| `peak_period` | Derived from `hour` | Commute peak, daytime, or off-peak |

The synthetic CSV also contains `traffic_volume`, `average_speed`, and `ev_count` for studying the generator and making EDA charts. They are **not** inputs to the deployed model. The target generator uses them, so held-out scores are only an educational check on synthetic data and are not evidence of field accuracy.

The training script computes MAE, MSE, RMSE, R², and feature importance from its held-out synthetic records. See `models/model_metrics.json` and `models/feature_importance.json` for the values from the included run.

## Caching and local storage

SQLite is created automatically at `ev_charging.db` on first run. The app migrates the previous project's prediction table when needed and stores:

- `predictions`: input summary, prediction mode/time, source metadata, and estimate;
- `historical_analysis`: saved selected-period rows, summary, chart references, and sources;
- `weather_cache` and `traffic_cache`: provider payloads with retrieval and expiry times.

Default cache lifetimes are 20 minutes for current weather, 30 minutes for forecast weather, 12 hours for historical weather, and 5 minutes for current traffic. If a refresh fails, the app may use an expired entry and labels it stale. Set `EV_DB_PATH` to use a different SQLite file.

## Dashboard and reports

The dashboard separates saved SQLite prediction counts from training-data charts. Training observations are calculated from the current synthetic CSV and are labelled synthetic. Historical analyses create six charts and a report with a summary, calculated observations, source list, model metrics, feature importance, limitations, and future-scope notes. Open a report from **History and Reports**; use **Download this report as HTML** for a self-contained file with its charts and styles embedded. The report page can also be printed or saved as PDF through the browser.

## Setup and run

Use Python 3.10 or newer.

```powershell
cd path\to\EV_Charging_Forecasting
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

The generated CSV, fitted model, metrics, charts, notebook, and SQLite database are included. To regenerate data and retrain:

```powershell
python generate_data.py
python train_model.py
```

Optional live traffic setup:

1. Copy `.env.example` to `.env`.
2. Set `TOMTOM_API_KEY` to a key from your TomTom developer account.
3. Restart the app. Without the key, traffic is labelled unavailable and the model receives `unknown`.

Run the app:

```powershell
python app.py
```

Then open <http://127.0.0.1:5000>. For the notebook, open `notebooks/EV_Charging_Forecasting.ipynb` from this project folder using Jupyter. Its optional API examples catch service and network errors and describe the source status.

## Limitations and next steps

- Synthetic training labels do not show real charging activity and cannot prove generalization.
- A random row split does not test a future period or a different city dataset.
- Historical Open-Meteo weather is reanalysis; future weather outside the API horizon is an analogue, not a forecast.
- Optional TomTom data refers to one nearby road segment, and requires its own key and terms of use.
- Real station sessions, EV counts, citywide traffic volume, historical traffic, charger availability, and local events are not included.

Next steps could use permitted station-level sessions and traffic measurements, evaluate on a chronological holdout, compare with simple baselines, and add uncertainty estimates after suitable real data becomes available.
